# Robots
Проект по изучению концепций OO-дизайна и разработке MDI-приложений на Java

Задача 1.1: Научиться собирать проект с использованием Apache Maven.

	Умение собирать код без среды разработки необходимо для того, чтобы организовать рабочий процесс — 
	код нужно регулярно собирать, проверять что он компилируется, а потом, для того чтобы убедиться в 
	работоспособности кода, прогонять тесты.
	
	Система сборки это программа, которая собирает другие программы. На вход система сборки получает 
	исходный код, а на выход выдаёт программу, которую уже можно запустить. Система сборки вызывает компилятор 
	при своей работе, а компилятор о существовании системы сборки даже не подозревает.(сборка, помимо компиляции, 
	включает в себя ещё целый спектр задач. Например, если программе для работы нужны какие-нибудь картинки, 
	то положить их в директорию с программой — задача системы сборки. Если программе нужны сторонние библиотеки, 
	то положить их в директорию с программой — задача системы сборки.)
	
	В рамках задачи сделано: 
	
		1. Создан файл конфигурации Maven — pom.xml, в нем описаны:

			- Идентификаторы проекта (groupId, artifactId, version)
			- Версия Java для компиляции и запуска (21)
			- Расположение исходного кода (папка src/)
			- Главный класс приложения (gui.RobotsProgram)
			- Плагин для создания исполняемого JAR-файла

		2. Настроена система сборки:
		
			- Проект собирается командой mvn clean compile:
				    clean — удаляет предыдущие результаты сборки
					compile — компилирует исходный код в байт-код (.class файлы)
			
			- Создаётся исполняемый JAR-файл командой mvn package:
					Упаковывает скомпилированные классы в JAR-архив
					Результат: target/Robots-X.X-SNAPSHOT.jar

Задача 1.2: Провести рефакторинг и исправить баг.

	Первая часть задачи..
	
	В рамках первой части задачи сделано:
		ляляля
	
	Вторая часть задачи - исправить баг. В исходной реализации была обнаружена утечка памяти, 
	связанная с неправильной работой слушателей событий лога. Когда пользователь закрывал окно, LogWindow оставался 
	в памяти, потому что LogWindowSource продолжал хранить на него ссылку в списке слушателей. Сборщик мусора не мог 
	удалить объект, так как на него была активная ссылка. При каждом новом сообщении вызывался метод onLogChanged() у 
	закрытого (уже невидимого) окна.
	
	В рамках второй части задачи сделано:
	
		- Добавлена отписка от лога при закрытии окна (LogWindow.java) (Теперь при закрытии окна оно явно отписывается 
		  от источника логов, удаляя себя из списка слушателей. Это гарантирует, что закрытое окно больше не будет получать 
		  уведомления и может быть корректно удалено сборщиком мусора.)
		  
		- Изменён тип коллекции для хранения сообщений (LogWindowSource.java) (LinkedList эффективнее удаляет первый элемент 
		  (самое старое сообщение), так как удаление в начале списка выполняется за константное время O(1), в отличие от ArrayList, 
		  где при удалении первого элемента приходится сдвигать все остальные элементы.)
		  
		- Добавлено ограничение на количество хранимых сообщений (Теперь лог хранит только последние 100 сообщений. При добавлении 
		  нового сообщения, если размер очереди превышает лимит, самое старое сообщение автоматически удаляется. Это предотвращает 
		  бесконечный рост потребления памяти при длительной работе приложения.)
		
		- Вместо прямых (сильных) ссылок на слушателей теперь используются слабые ссылки (WeakReference). Сборщик мусора может удалить 
		  объект, даже если на него есть слабые ссылки (в отличие от сильных, которые препятствуют удалению).
		  
		- Добавлен кэш активных слушателей для оптимизации (Поскольку работа со слабыми ссылками требует проверки, жив ли ещё объект, 
		  эта операция может быть затратной при большом количестве сообщений. Для оптимизации добавлен кэш активных слушателей — массив, 
		  который содержит только живые объекты. Кэш формируется при первом уведомлении после изменений в списке слушателей и используется 
		  для последующих уведомлений, пока список не изменится (при добавлении или удалении слушателя кэш сбрасывается). )
